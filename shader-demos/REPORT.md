# Shader Demos 製作報告

十六個以原生 WebGL 即時運算的畫面練習，外加一個目錄頁。每一頁都是完全獨立的單一 HTML 檔，
CSS 與 JavaScript 內嵌，沒有任何外部函式庫、CDN、遠端字型或圖片，所有畫面素材都由程式生成。

- 目錄頁：[`shader-demo-list.html`](shader-demo-list.html)
- 開啟方式：直接雙擊開檔（`file://`）或放進任何靜態伺服器都可以

## 二、驗證結果

**全部 17 頁皆以瀏覽器實測，沒有任何一頁是「僅靜態檢查」。**

測試方式：Playwright 1.49 驅動 Chromium（`--use-angle=swiftshader` 軟體算繪），
每頁分別以 1440×900 與 390×844 開啟並執行約 4.5 秒後檢查。

| 檢查項目 | 結果 |
| --- | --- |
| console error | **0**（17 頁合計） |
| 未捕捉的例外 | **0** |
| 失敗的網路請求 | **0** |
| 錯誤提示畫面（fallback）被觸發 | **0 頁** |
| 水平捲動溢出 | **0 px**（兩種尺寸、全部頁面） |
| WebGL2 context 建立成功 | 16 / 16 |
| 浮點 render target 可用 | 16 / 16 |
| 畫面內容檢查 | 16 / 16 通過 |

畫面內容檢查以 Pillow 取樣每張截圖的中段區域，要求亮度標準差 ≥ 6、
動態範圍（p99−p1）≥ 22、量化後的色調數 ≥ 3、且沒有單一顏色佔超過 90%。
最終實測：色調數 6–73、動態範圍 43–215，全部通過。

另外單獨驗證了 `file://` 直接開檔的路徑（8 個代表性頁面，含目錄頁與三個多重緩衝的頁面）：
無 console error、無失敗請求，`readPixels` 取樣確認畫面有實際內容而非空白。

唯一出現的 4 筆 console warning 是 `GPU stall due to ReadPixels`，
由驗證腳本自己呼叫 `toDataURL()` 截圖造成，不是頁面本身產生的。

### 審片過程中修掉的問題

逐張檢視截圖後重做了三輪，比較值得記下來的：

1. **錯誤提示框在每一頁都蓋住畫面。** `#fallback{display:grid}` 的特異性高於瀏覽器內建的
   `[hidden]{display:none}`，所以 `hidden` 屬性根本沒生效。而我第一版的檢查讀的是
   `fb.hidden` 屬性，屬性確實是 `true`，所以完全沒驗出來——十六頁都在顯示錯誤訊息，
   數據卻一片綠。改成 `#fallback[hidden]{display:none}`，檢查也改成讀 computed display。
2. **光軌在低畫格率下斷成虛線。** 原本每幀只在光點「當下的位置」畫一個高斯點，
   畫格率一低，相鄰兩幀之間就留下空隙。改成沿著這一幀真正走過的弧線補六個取樣點
   （需要知道 `dt`，所以新增了 `uDt` uniform），任何畫格率下軌跡都是連續的。
3. **沒有人操作時，游標的光點杵在畫面正中央不動。** 新增 `uActive`，游標真的移動過才畫。
4. **摩爾紋看不出來。** 原本用兩層覆蓋率相乘，但織物的覆蓋率幾乎處處接近飽和，乘積沒有低頻成分。
   改成直接取兩層經紗／緯紗的相位差 `cos((φA−φB)·2π)`，拍頻乾淨且可控，也不必靠取樣混疊碰運氣。
5. **雕塑出框、人像被裁掉頭頂。** 兩頁的構圖都超出畫面，調整了 SDF 的整體縮放與剪影比例。
6. **漸層網格糊成一團土色。** 距離權重的 epsilon 太大（0.052），五個色點平均之後所有顏色都抵消了，
   收到 0.016 之後色塊才各自成立。

## 三、自行做出的重要決定

使用者休假中無法詢問，以下是遇到規格沒寫清楚時自己做的判斷與理由。

**1. 一律用 GLSL ES 1.00 撰寫 shader，而不是 WebGL2 專用的 `#version 300 es`。**
WebGL2 的 context 同樣接受 ES 1.00 的 shader，所以一份原始碼就能同時跑在 WebGL2 與 WebGL1 上，
不必為降級路徑維護第二份 shader。WebGL2 的好處（`RGBA16F`、`EXT_color_buffer_float`）仍然拿得到。

**2. 像素排序做成「持續進行中」而不是「排完為止」。**
完整排序一個 1080 像素高的欄位需要約 1080 個 pass，不可能維持 60fps。
改成每幀跑 14 個 pass、讓排序逐步收斂，並且每幀隨機把少量像素換回原值，
所以它永遠差一點點排不完——這同時解決了效能問題，也讓畫面一直是活的。

**3. 第 14 頁刻意不用反應擴散的變體。**
規格說它必須與第 07 頁「在視覺與手法上明顯不同」。第 07 頁是連續的偏微分方程（Gray-Scott），
第 14 頁改用離散的細胞自動機：三個狀態（佔據／年齡／痕跡）、鄰居越少反而越容易被佔據（長出絲狀前緣）、
細胞老死後留下會壓抑再生的痕跡。因此它長出的是會往外擴張的環狀菌落，而不是珊瑚。

**4. 新增 `?grab` 查詢參數。**
無頭 Chromium 的合成層抓不到 `preserveDrawingBuffer:false` 的 WebGL canvas。
與其為了測試而讓所有頁面永遠付出保留緩衝區的成本，不如讓它只在網址帶 `?grab` 時開啟。
正常瀏覽時行為完全不變，而任何人想截圖這些頁面也用得到。

**5. 保留「隱藏說明」切換。**
規格要求文字退到邊緣、每頁最多 3 個控制項。那三個控制項留給 shader 參數，
另外在右上角放一個把所有文字收起來的開關——它不是參數，是看作品用的。

**6. 自動降解析度的判斷放在前 3 次、每 30 格一次。**
原本設 70 格，在一台只有 10fps 的裝置上要等 7 秒才會反應，太慢了。

**7. 水面高度場以 `h×0.5+0.5` 編碼。**
波動方程需要負值，但降級到 8 位元材質時存不了負數，統一編碼之後兩種精度共用同一份 shader。

## 四、已知限制

- **浮點材質不支援時的降級。** 第 03、06、07、14、15 頁會依序嘗試
  `RGBA16F` → `RGBA32F` → `RGBA8`，並檢查 framebuffer 是否完整。
  退到 8 位元時：液態位移的漣漪會出現可見的階梯，長時間曝光的光點亮度會自動調低（避免很快燒白），
  反應擴散的濃度解析度降低、圖樣邊緣較粗。生長與菌落本來就是離散狀態，8 位元沒有差別。
  若連 8 位元的 framebuffer 都建不起來，這幾頁會停止算繪並顯示說明文字，不會是空白頁。
- **本次實測跑在 SwiftShader 軟體算繪上**，畫格率約 6–15fps。這證明了正確性與相容性，
  但無法證明「一般筆電 60fps」這個效能目標——那需要在真實 GPU 上量測。
  也因為畫格率低，自動降解析度的機制在這次測試中只觸發了一次，沒有被充分驗證。
- **第 09 頁（光線步進）最耗效能**，每像素最多 72 次步進。它的渲染像素預算已經單獨調低到 1.25M，
  但在老舊的行動裝置上仍可能是十六頁裡最吃力的一頁。
- **觸控裝置沒有 hover。** 游標互動在手機上以觸控拖曳代替（canvas 設了 `touch-action:none`），
  但「滑過」這類不按下的互動在手機上無法重現；這幾頁在沒有互動時都有自走的動態，不會是靜止的。
- **縮圖是某一瞬間的截圖。** 第 07、14 頁會持續生長變化，實際開啟後看到的畫面不會和縮圖一樣。
- **`prefers-reduced-motion` 的處理是放慢而非完全靜止**（時間以 0.14 倍前進，模擬步數降到 35%）。
  完全凍結會讓反應擴散與生長這兩頁失去意義，所以選擇大幅放慢。
